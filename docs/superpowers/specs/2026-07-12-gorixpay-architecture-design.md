# GroixPay 架构设计

## 1. 文档信息

* 项目名称：GroixPay

* 设计日期：2026-07-12

* 项目目标：使用 Go 与 React 完整重构彩虹易支付 Epay，在保持既有 API、签名、响应及通知协议兼容的前提下，改善资金一致性、性能、安全性、可测试性与部署体验。

* 参考系统：`Epay/`

* 迁移方式：新系统一次性重构并整体切换，不保留 PHP 运行时。

## 2. 设计原则

1. 资金正确性优先于吞吐量和开发便利性。
2. 外部协议完全兼容，内部模型不继承历史耦合。
3. 核心正确性不依赖 Redis 或外部消息队列。
4. 同一套代码正式支持 SQLite、MySQL 5.7+ 与 PostgreSQL。
5. 模块边界清晰，首版保持模块化单体，避免过早微服务化。
6. 支付插件使用显式契约，渠道差异不得泄漏到订单核心。
7. 安全、审计、迁移和可观测性属于首版能力，而非后续补丁。

## 4. 总体架构

```text
浏览器 / 商户系统 / 支付平台
              │
        Gin HTTP Router
              │
  ┌───────────┴────────────┐
  │ Epay 兼容接口          │
  │ GroixPay 管理 API      │
  │ React 静态资源         │
  └───────────┬────────────┘
              │
       Application Services
              │
  ┌───────────┼────────────┐
  │ 商户权限  │ 支付订单   │
  │ 渠道插件  │ 退款关闭   │
  │ 资金账本  │ 结算代付   │
  │ 分账风控  │ 通知任务   │
  └───────────┬────────────┘
              │
        GORM + 原生 SQL
              │
 SQLite / MySQL / PostgreSQL
              │
       Transactional Outbox
              │
    内置 Worker / 可选 Redis
```

一个 Go 代码库生成统一镜像和二进制。默认进程可同时运行 Web 与 Worker，也允许通过子命令或启动参数将 Worker 独立部署。React 构建产物可嵌入 Go 二进制，也可由反向代理独立托管。

## 5. 领域模块

| 模块             | 职责                              |
| -------------- | ------------------------------- |
| `identity`     | 管理员与商户登录、Session、Token、MFA、RBAC |
| `merchant`     | 商户资料、分组、费率、凭据、实名与账户视图           |
| `payment`      | 下单、查询、关闭、订单状态机与收银台              |
| `channel`      | 支付类型、渠道账户、路由、轮询、限额与费率计算         |
| `plugin`       | 插件契约、能力注册、渠道请求与回调验证             |
| `refund`       | 退款申请、渠道退款、退款查询与状态机              |
| `ledger`       | 不可变资金账本、余额快照、冻结与解冻              |
| `settlement`   | 商户结算、批次、手续费与出款                  |
| `transfer`     | 代付申请、查询、凭证与状态流转                 |
| `profitshare`  | 分账接收方、分账订单、回退与查询                |
| `risk`         | 限额、黑名单、域名、地区、商品与频率规则            |
| `notification` | 商户异步通知、签名、回执与重试                 |
| `outbox`       | 可靠任务、租约、退避、死信与幂等执行              |
| `audit`        | 管理操作、登录、安全与资金审计                 |
| `compat`       | Epay 旧版和新版 API 的请求及响应适配         |
| `system`       | 配置、文件、健康检查、指标与系统维护              |

模块通过公开应用服务交互。禁止处理器直接操作仓储，禁止跨模块直接更新数据表，禁止插件直接修改订单或资金状态。

## 6. 数据架构

### 6.1 跨数据库约束

* 主键使用应用生成的 UUIDv7，外部可见交易号使用独立兼容编号。

* 金额统一使用最小货币单位的 `BIGINT`，人民币以分存储，禁止浮点运算。

* 时间统一以 UTC 存储，在兼容 API 与界面边界进行时区转换。

* JSON 配置由统一序列化类型处理，不依赖单一数据库的 JSON 查询能力。

* 通用 CRUD 使用 GORM，资金锁、任务租约和复杂报表使用方言适配 SQL。

* 迁移脚本和 Repository 集成测试必须覆盖三种数据库。

* SQLite 采用 WAL、busy timeout 和受控连接数；单实例只允许一个活跃 Worker。

### 6.2 核心实体

* 身份：管理员、商户、角色、权限、角色绑定、会话、API 凭据。

* 渠道：支付类型、渠道、渠道账户、渠道能力、路由规则、轮询策略。

* 交易：支付订单、支付尝试、渠道回调、商户通知、退款单。

* 资金：资金账户、账本交易、账本分录、余额快照、冻结记录。

* 出款：结算单、结算批次、代付单、转账凭证、分账单。

* 平台：Outbox 任务、任务执行、死信、风控规则、审计日志、系统配置。

### 6.3 关键约束

* 支付订单对 `(merchant_id, out_trade_no)` 建立唯一约束。

* 渠道回调以渠道流水号和回调摘要实现双重幂等。

* 每次资金动作必须携带全局唯一业务幂等键。

* 账本分录只允许追加，不允许更新和删除。

* 余额变化、账本分录、业务状态与 Outbox 必须在同一事务提交。

* 订单、退款、结算、代付和分账使用显式状态机，非法转换立即拒绝。

* 数据库约束与应用校验共同保障完整性，不依赖单一层级。

## 7. 资金一致性与异步任务

核心资金事务按以下顺序执行：

1. 根据业务幂等键检测重复请求。
2. 锁定订单或资金账户。
3. 验证当前状态与状态转换。
4. 更新业务实体。
5. 写入平衡的账本交易与账本分录。
6. 更新余额快照。
7. 写入 Outbox 任务。
8. 提交事务后由 Worker 执行通知或后续动作。

Outbox 数据库表是任务事实来源。Worker 使用租约抢占、幂等消费者、指数退避和随机抖动；超过重试阈值的任务进入死信，管理后台可查看、重试或终止。Redis 仅用于任务唤醒、缓存、限流、会话和多实例协调，Redis 故障不得导致任务丢失或资金结果变化。

## 8. Epay API 完全兼容

### 8.1 兼容入口

* `/submit.php`

* `/mapi.php`

* `/api.php`

* `/api/{class}/{method}`

* `/pay/{method}/{trade_no}/`

* 原系统同步返回、异步通知、收银台和支付结果相关路径

### 8.2 兼容范围

* GET 与 POST 接收方式。

* 参数名称、必填规则、默认值和空值处理。

* MD5、RSA 签名字段筛选、排序、拼接及验签语义。

* 旧版成功码 `1`、新版成功码 `0` 及各自错误语义。

* JSON、HTML、跳转、二维码、URL Scheme、JSAPI、App 和小程序响应。

* 商户同步返回与异步通知字段、签名和成功回执文本。

* `.php` 后缀历史路径、平台交易号格式和商户订单唯一规则。

兼容层把历史请求转换为内部标准命令，并把领域结果转换为历史响应。兼容 DTO、错误码和签名逻辑不得进入领域模块。使用固定请求、响应和签名向量进行字节级契约测试。

GroixPay 自有管理 API 使用 `/api/v1/`、统一 JSON 响应、统一错误码与 OpenAPI 3.1。管理端采用 Session 与可撤销 Token；外部商户接口继续采用 Epay 签名鉴权。

## 9. 支付插件架构

插件采用编译期注册的 Go 实现，不加载不受信任的动态二进制。插件元数据声明支持的支付方式、地区、货币和能力，能力接口按需实现：

* 创建支付

* 查询支付

* 关闭支付

* 申请退款

* 查询退款

* 发起代付

* 查询代付

* 验证回调

* 渠道健康检查

统一支付动作包括跳转 URL、HTML、二维码、URL Scheme、JSAPI、App 参数、小程序参数和付款码结果。插件只负责渠道协议、签名、证书、错误映射和回调验真，不得直接更新订单、账本或余额。

首批实现支付宝官方及必要服务商能力、微信支付 V3 的 Native/JSAPI/H5/App/小程序及服务商模式、彩虹易支付兼容上游和 Jeepay 兼容上游。其他 Epay 插件按照使用优先级分批迁移。

## 10. 身份、权限与安全

* 管理端和商户中心使用安全 Cookie Session，前后端 API 使用可撤销 Token。

* 运营后台采用 RBAC，支持角色、权限点和数据范围。

* 支持 TOTP MFA、登录设备查看、会话撤销和高风险操作二次验证。

* 新密码使用 Argon2id；迁移的旧密码在成功登录后自动升级。

* Cookie 使用 `HttpOnly`、`Secure` 和合理的 `SameSite` 策略。

* 登录、下单、查询和回调按 IP、商户、接口及风险等级分别限流。

* 渠道密钥、商户私钥和证书口令使用 AES-256-GCM 信封加密。

* 主密钥由环境变量、Docker Secret 或只读挂载文件提供，并支持版本和轮换。

* 日志、错误、指标和审计输出统一脱敏密码、Token、密钥、证书、银行卡及身份信息。

* 资金与安全操作写入不可篡改语义的独立审计记录。

## 12. 部署与配置

### 12.1 轻量模式

* 单 Go 二进制或单 Docker 容器。

* 内嵌 React 静态资源。

* SQLite 数据文件、上传文件和证书目录使用持久化卷。

* 内置 Worker，不依赖 Redis。

* 面向开发、演示和低流量单机部署。

### 12.2 标准模式

Docker Compose 默认包含 GroixPay Web、GroixPay Worker、PostgreSQL 和 Redis。Web 与 Worker 使用同一镜像，通过启动命令区分角色。生产环境可增加反向代理和外部可观测性组件。

配置优先级为：命令行参数、环境变量、配置文件、默认值。敏感配置不得写入镜像、前端产物或版本库。

## 13. 可观测性

* 使用 `slog` 输出 JSON 结构化日志。

* 请求、订单、渠道尝试、回调和任务共享可关联追踪标识。

* 提供存活检查与就绪检查。

* 暴露 HTTP、数据库、订单、渠道、通知、任务和资金异常指标。

* 提供 Prometheus 指标与 OpenTelemetry 接口，追踪后端为可选依赖。

* 审计日志与普通运行日志分离。

* SQLite 轻量模式默认关闭高成本指标，可按配置启用。

## 14. Epay 历史数据迁移

提供独立 `migrate-epay` 命令，只读连接原 Epay MySQL 数据库并完成：

1. 检查原系统版本、表结构和数据质量。
2. 迁移系统配置、商户、分组、渠道和插件配置。
3. 迁移订单、退款、结算、代付、分账和资金记录。
4. 将十进制金额严格转换为整数最小货币单位。
5. 重建账户余额与账本期初分录。
6. 校验记录数、金额汇总、状态分布和关联完整性。
7. 输出 Markdown 与 JSON 迁移报告。

迁移工具支持预演、分批、断点续传和幂等重跑。正式切换时旧系统必须进入只读或停机状态；迁移完成且校验通过后才允许启动 GroixPay 写流量。无法安全转换的密钥或异常数据进入阻断清单，不允许静默跳过。

## 15. 测试与质量门禁

* 单元测试覆盖金额、签名、费率、路由、状态机和风控。

* Epay 契约测试覆盖请求、响应、错误码、签名和通知回执。

* 三数据库运行同一组迁移与 Repository 集成测试。

* 插件通过 HTTP Mock 验证请求签名、回调、超时和错误映射。

* 资金测试验证借贷平衡、幂等、并发回调、死锁重试和事务回滚。

* 迁移测试使用脱敏数据快照验证记录与金额汇总。

* React 使用 Vitest 与 Testing Library，核心链路使用 Playwright。

* CI 执行格式检查、静态分析、单元测试、集成测试、前端测试和镜像构建。

任何账本不平衡、API 契约变化、三数据库迁移失败或高危安全检查失败均阻断发布。

## 17. 实施边界与顺序

首版必须交付完整的核心领域、Epay API 兼容、全量页面、历史数据迁移框架和首批支付插件。其余约 62 个历史插件分批迁移，不阻塞核心平台建设。

建议实施顺序：

1. 建立工程基础、配置、三数据库迁移、日志与测试基线。
2. 实现身份、RBAC、商户、系统配置和密钥管理。
3. 实现账本、订单状态机、Outbox 与幂等基础设施。
4. 实现渠道、路由、费率、风控和支付插件契约。
5. 实现 Epay 下单、查询、关闭、退款与通知兼容。
6. 实现结算、代付、分账和资金管理。
7. 实现首批支付插件及插件契约测试。
8. 实现 React 管理端、商户端、官网、文档与收银台。
9. 实现全量历史迁移、校验报告和切换流程。
10. 完成安全、性能、故障恢复与三数据库验收。

## 18. 验收标准

* 已覆盖的 Epay 接口在固定契约样本上实现请求、签名、响应和通知兼容。

* 同一商户订单的并发创建不会生成重复有效订单。

* 重复和乱序回调不会重复入账或导致状态回退。

* 所有资金交易保持账本借贷平衡，并可追溯到业务单据。

* Redis 不可用时核心支付、通知和任务可继续可靠运行。

* SQLite、MySQL 5.7+ 与 PostgreSQL 均能完成初始化、升级和核心测试。

* Epay 全量迁移报告中的记录数、金额和状态校验通过。

* 单容器与 Docker Compose 两种部署模式均可完成支付闭环。

* 管理后台、商户中心、官网、开发文档和收银台满足原系统主要功能范围。

* 不在日志、接口、镜像或仓库中泄露密码、Token、渠道密钥和证书内容。

* Redis 为可选增强依赖。
